# Spec: Menus

Menus for StylesUI: dropdown menus from buttons, user menus, row actions, application menubars, context menus, comboboxes, and the navigation menus of content sites such as blogs. Everything must be fully accessible and work with the keyboard as each pattern's users expect.

This is the capability map for the initiative and the decisions every part shares. The requests bundle five components that can each be built, tested and shipped on their own, so each module gets its own spec, written in build order once this map is approved. The module specs hold the APIs, keyboard tables and success criteria in detail; this document holds what they must all agree on.

## Objective

Users are app and site developers building with StylesUI. They need:

- **Content sites** (blogs, docs, marketing): a header whose sections open into lists or columns of links, collapsing to one "Menu" on a phone.
- **Apps**: a "⋯" actions menu on a row, a user menu from an avatar, "New ▾" and view-options menus, with submenus, checkbox and radio items, shortcuts and destructive items.
- **App-like tools** (editors, design tools, admin consoles): a menubar and context menus.
- **Pickers**: choosing from rich options, such as people with avatars, and autocomplete with filtering.

Success looks like this: each use case above is built from StylesUI components alone, passes axe and a keyboard story in every mode and theme, and follows its WAI-ARIA Authoring Practices pattern, with no consumer writing focus or ARIA code of their own.

## Assumptions

1. The browser floor stays the overlays' (Chrome 129, Firefox 147, Safari 26). Menus use `popover` and CSS anchor positioning with no polyfill and no positioning library.
2. No new runtime dependencies. New icons are copied from `lucide-static`, as the existing ones are.
3. Each module has its own spec, named `<date>-menus-<module id>.md` and listed in [README.md](README.md), and its own pull request.
4. The combobox reuses Listbox's internals (`aria-activedescendant`, option ids, type-ahead), moving what both need into a shared folder, rather than rendering `Listbox` itself.
5. Breaking changes are acceptable while the package is in beta, though none is expected.
6. The design mockups behind this spec were generated outside the repository and are not kept: this text is the record.

## Decisions

Agreed on 2026-10-21 from the design mockups:

- **Two families, not one.** Site navigation is a disclosure: a button with `aria-expanded` and a panel of ordinary links, with no `menu` role. App commands are ARIA menus (`menu`, `menuitem`, `menuitemcheckbox`, `menuitemradio`). `role="menu"` on site navigation puts screen readers into application mode, stops links being announced as links and breaks Tab, so no StylesUI navigation component uses it.
- **Highlight: tint plus inset ring.** The item under the pointer takes `--sui-color-secondary-subtle`. Keyboard focus adds the inset focus ring, as Listbox's active option does, and that ring on `secondary-subtle` is already a pairing the Contrast stories assert. A destructive item takes `--sui-color-danger-subtle` in place of the tint. A solid primary fill (option B) was rejected because in Listbox a solid fill means selected, and a start bar (option C) because in NavList it means the current page and is a weak focus indicator.
- **Selection is a shape.** Checked and selected states are a check mark or a radio dot in the leading column, never a fill, so they don't depend on colour (1.4.1) and never clash with the highlight.
- **Focus model.** Menus move real DOM focus between items (roving), which assistive technology, VoiceOver on iOS included, handles best. The combobox keeps focus in its input and points `aria-activedescendant` at the active option, because the user is typing there.
- **Pointer and keyboard share one active item.** Moving the pointer over an item makes it the active item, as in the WAI-ARIA menu examples, so the arrow keys continue from where the pointer was.
- **Site navigation opens on click only.** No hover-open, so 1.4.13 doesn't apply and panels don't open as the pointer passes.
- **Mobile navigation is a push-down disclosure.** The same links in one "Menu" disclosure that pushes the page down, needing no focus trap. A modal sheet may come later as an option.
- **Menus first.** The menu button comes first; the combobox comes last.
- **Stacked pull requests.** One focused pull request per module, stacked in build order, each based on the one before: `menu` (which also carries this map), `site-nav`, `context-menu`, `menubar`, `combobox`. `site-nav` needs nothing from `menu` but stacks on it to keep one line of review.
- **Hook plus parts.** As with `usePopover` and `Popover`, a hook owns the open state and hands out `getTriggerProps()` and `getMenuProps()`, and parts render the menu. A convenience wrapper such as `<MenuButton label>` may follow.

## Modules

These are the scopes each module spec starts from. The keys follow the WAI-ARIA Authoring Practices patterns named; each module spec gives the full table.

### `menu`

The [menu button](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/) and [menu](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/) patterns. Uses: row actions, user menus, "New ▾", sort and view options.

- **Parts.** `useMenu`, `Menu`, `MenuItem` (a button by default, or `as="a"` or a router link, as `NavListItem` takes), `MenuItemCheckbox`, `MenuRadioGroup` with `MenuItemRadio`, `MenuGroup` (named by a visible label), `MenuSeparator` and `Submenu`.
- **Rows.** A 1rem leading slot for an icon, check or radio dot, so labels line up; the label with an optional description; and something trailing, either a shortcut, `aria-hidden` and announced through the item's `aria-keyshortcuts`, or a submenu chevron that mirrors in right-to-left text. A `danger` tone and `disabled` items, which are `aria-disabled` and still reached by the arrow keys.
- **Keys.** On the trigger, Enter, Space or ↓ opens on the first item and ↑ on the last. In the menu, ↑ ↓ move, Home and End go to the ends, type-ahead from `src/collections` moves by label, → opens a submenu and ← or Escape closes one level, returning focus to the item or trigger that opened it. Tab closes every open menu and moves on, without trapping focus. Keys pressed with Alt, Ctrl or Meta are left alone.
- **Overlay.** `popover="auto"` and anchor positioning, so the browser closes a menu on Escape and on a click outside, and flips it at the window's edge. A submenu is a nested popover, so opening it keeps its parent open.
- **Density.** `compact` (about 26px rows, for menubars and dense tools) and `default` (32px), with rows at least 44px under `(pointer: coarse)` whatever the density.
- **Out of scope:** press-drag-release selection, a convenience `MenuButton`, split buttons.

### `site-nav`

The [disclosure navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/) pattern. Uses: blog, docs and marketing headers.

- **Desktop.** A section ("Topics ▾") is a button with `aria-expanded` that opens a panel of links, as a list or in columns with descriptions. Links keep link semantics and Tab walks them. Escape closes the panel and returns focus to its button; a click outside or focus leaving the panel closes it.
- **Narrow.** The header collapses to one "Menu" disclosure holding the same links, which pushes the page down. Sections become nested lists that expand in place. Rows are at least 44px, and the current page uses NavList's current-item look.
- **Current page.** `aria-current="page"`, shown by an underline in the bar and NavList's bar in the narrow list, so not by colour alone.
- **Out of scope:** hover-open, a modal sheet on mobile, mega menus with images or promotional content.

### `context-menu`

The `menu` pattern opened by `contextmenu`. Uses: secondary actions on a file, row or canvas object in an app.

- Opens at the pointer on right-click, at the focused element on Shift+F10 or the ContextMenu key, and on a long-press where the platform sends no `contextmenu`, as iOS Safari does not.
- Anchored to a zero-size point placed at the pointer, so it flips at the window's edges like any overlay.
- Opt-in per region. It never replaces the native menu on text fields, and the docs require every action in it to be available somewhere visible too.

### `menubar`

The [menubar](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/) pattern. For app-like tools only; the docs steer content sites to `site-nav`.

- One tab stop. ← → move across the bar, and while a menu is open, moving across the bar opens the next item's menu instead, by key or by pointer. ↓, Enter or Space opens a menu; Escape closes it and returns focus to the bar.
- Every menu in the bar takes the `compact` density.

### `combobox`

The [combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/) pattern with a `listbox` popup. Uses: rich pickers, where a native `Select` cannot show avatars, and autocomplete.

- **Select-only:** a button-like field that opens the list; type-ahead moves through it.
- **Autocomplete:** an input that filters the list as the user types. The number of results is announced politely (4.1.3).
- ↓ or Alt+↓ opens, ↑ ↓ move the active option, Enter commits, Escape closes and then clears. Moving through options never commits or navigates (3.2.2).
- Selection is a check mark and the active option is the inset ring, never a fill.
- **Out of scope:** multiple selection, creating options, a command palette.

## Visual language

Every popup list, whether a menu or a combobox's list, is drawn by one internal surface owned by the `menu` module, whose CSS module the others share, as `TextControl` does for the text inputs.

- **Surface.** The same as Popover: `--sui-color-overlay`, a `--sui-border-width` border in `--sui-color-border`, `--sui-radius-lg`, `--sui-shadow-sm` and `--sui-space-1` padding. In `playful` this gives the ink outline and hard shadow with no extra rules. At least 12rem wide and at most `min(20rem, 100vw - margins)`, so it reflows at 320px.
- **Rows.** `--sui-font-size-sm` at `--sui-line-height-tight`, `--sui-space-2` between columns, `--sui-radius-md` corners, and a minimum height rather than a fixed one (1.4.12). Icons, descriptions, shortcuts and the chevron use `--sui-color-text-muted`, and a check or radio dot uses `--sui-color-text`.
- **Groups and separators.** A group label is `xs` bold muted text lined up with the item labels. A separator is a `--sui-color-border` rule across the full width of the surface.
- **Highlight tokens.** Read but never declared, like Listbox's selection tokens, so an ancestor can restyle them: `--sui-menu-highlight` (default `--sui-color-secondary-subtle`), `--sui-menu-on-highlight` (default `--sui-color-text`) and `--sui-menu-danger-highlight` (default `--sui-color-danger-subtle`). The keyboard ring is always `--sui-color-focus-ring` at `--sui-focus-ring-width`, inset. The `menu` spec fixes the final names.
- **Disabled.** Dimmed by mixing the text colour to half strength, not by `opacity`, so the focus ring keeps full strength, as Listbox's disabled options are.
- **Motion.** Fade and a short move out from the trigger, as Popover does; under reduced motion, only the fade.
- **Forced colours.** The highlight is `Highlight` with `HighlightText`, checks and dots take the text colour, and a disabled item is `GrayText`.

## Accessibility baseline

Every module meets these, and its keyboard story asserts the ones a test can reach:

- **2.1.1 Keyboard, 2.1.2 No keyboard trap:** every action works from the keyboard, and Tab always leaves.
- **2.4.3 Focus order:** focus goes back to the trigger, or the item that opened a submenu, when a menu closes with focus inside it.
- **2.4.7 Focus visible, 1.4.11 Non-text contrast:** `focusRingContrast(element) >= 3` on the focused item, the input of a combobox and every trigger, on every palette, mode and theme.
- **2.4.11 Focus not obscured:** an open site-nav panel closes when focus leaves it, so it never covers the focused element.
- **1.4.1 Use of colour:** checked state is a shape, a destructive item says so in its label, and the current page is underlined or barred.
- **1.4.3 Contrast:** muted text, shortcuts and descriptions keep 4.5:1 on the overlay and on the highlight. Pairings a test can't reach through axe, such as the highlight under hover, use `textContrast`.
- **1.4.10 Reflow, 1.4.12 Text spacing:** surfaces fit a 320px viewport, a submenu with no room on either side overlaps its parent, and rows don't clip with wider spacing.
- **1.4.13 Content on hover or focus:** nothing opens on hover except a submenu inside an open menu. A submenu waits briefly before opening on hover, and a diagonal pointer move towards it doesn't close it, so it stays put while the pointer reaches it.
- **2.5.2 Pointer cancellation:** items act on click, never on pointer down.
- **2.5.3 Label in name:** visible labels are the accessible names; shortcuts are `aria-hidden` and announced through `aria-keyshortcuts`.
- **2.5.8 Target size:** rows are at least 24px tall, and 44px under `(pointer: coarse)`.
- **4.1.2 Name, role, value:** triggers carry `aria-haspopup` and `aria-expanded`, items carry `aria-checked` and `aria-disabled`, groups are named, and a combobox carries `aria-expanded`, `aria-controls` and `aria-activedescendant`.
- **4.1.3 Status messages:** the combobox announces its result count.

## Code Style

Follow `docs/standards/` and the existing overlay hooks. The intended shape of the `menu` API, which its spec refines:

```tsx
const menu = useMenu({ placement: "bottom-end" });

<IconButton label="Actions" {...menu.getTriggerProps()}>
  <MoreHorizontalIcon />
</IconButton>
<Menu {...menu.getMenuProps()}>
  <MenuItem icon={<EditIcon />} onAction={edit} shortcut="⌘E">
    Edit
  </MenuItem>
  <Submenu label="Move to">…</Submenu>
  <MenuSeparator />
  <MenuItem onAction={remove} tone="danger">
    Delete…
  </MenuItem>
</Menu>
```

Every token read keeps a literal fallback equal to Bright's light value:

```css
.item[data-highlighted] {
  background-color: var(--sui-menu-highlight, var(--sui-color-secondary-subtle, #f3f4f6));
  color: var(--sui-menu-on-highlight, var(--sui-color-text, #111827));
}
```

## Testing Strategy

- **Unit (jsdom).** Keyboard logic, roles and ARIA state, focus movement, type-ahead, open state and the hook's prop merging, in each component's `.test.tsx`. Type-level rules (a required name, omitted props) through `// @ts-expect-error`.
- **Stories (Chromium, all four mode and theme projects).** Every component has a `KeyboardInteraction` story covering its pattern's keys, tab order, focus return and `focusRingContrast` on the focused element, with real input from `trustedInput()` where Chromium needs it (Escape, clicks outside, hover). Every story file sets `a11y.test: "error"`.
- **Contrast.** New pairings, such as muted text and the focus ring on the highlight, are added to `src/styles/Contrast.stories.tsx` for every palette.
- **By hand.** Fallback colour pairs, and each module's screen reader behaviour in VoiceOver (macOS and iOS) and NVDA, recorded in its pull request.

## Boundaries

- **Always:** run `pnpm verify` and the fallow audit before every commit. Give every token read a literal fallback. Keep docs in the same commit as the behaviour they describe. Add each new fixed-element component to the jsx-a11y component map.
- **Ask first:** pushing or opening a pull request; bumping the version or publishing; adding a dependency; changing an existing component's API or an existing colour; moving Listbox internals in a way that changes Listbox's behaviour.
- **Never:** use `role="menu"` for site navigation; open anything but a submenu on hover; lower a contrast threshold, skip an assertion or set a story to `a11y.test: "todo"`; edit `dist/`; hand-write a dependency version.

## Success Criteria

For the initiative; each module spec adds its own testable criteria.

1. Each of the five modules has its own approved spec in `docs/specs/`, listed in README.md, before its code is written.
2. Each use case in the Objective can be built from exported StylesUI components, shown by a story: row actions, a user menu with a radio submenu, a blog header with a section panel and its narrow "Menu", a menubar with a submenu, a context menu, a select-only picker and an autocomplete.
3. Every story file passes axe with `a11y.test: "error"`, and every interactive component's `KeyboardInteraction` story passes, in all four storybook projects.
4. No StylesUI navigation component renders `role="menu"`, `menubar` or `menuitem`.
5. A menu, a menubar's menus and a combobox's list render through the one shared surface, so the highlight tokens restyle all of them.
6. `pnpm verify`, `pnpm build` and the fallow audit pass after each module, and a throwaway consumer importing only `NavBar` bundles no menu code, and one importing only `Menu` bundles no combobox code.
7. `docs/design/concepts.md` describes each module, and AGENTS.md lists each component in its architecture and jsx-a11y sections.

## Open Questions

Resolved in review on 2026-10-21:

- **Mockups:** not kept.
- **Site-nav names and markup:** settled by the `site-nav` spec after a spike: `NavBar` and its parts, one DOM laid out by a container query, and panels positioned with anchor positioning rather than as popovers.
- **Checkbox and radio items:** Enter and a click toggle and close; Space toggles and keeps the menu open.
- **Pull requests:** one per module, stacked (see Decisions). Whether to release each as it lands is asked when the stack merges, since a version bump is an ask-first change.
